BLB Stage-2 RL 动作如何得到 total_bits、invalid_chain、fusion_count

本页说明当前代码里从强化学习动作到 Rescale_Optimizer 成本信号的真实调用链。 重点结论是：RL 的动作向量不会直接传给 Rescale_Optimizer；中间必须先经过 action_vec → BlockNoiseConfig → t_new + delta_overrides 这层语义映射。

生成日期：2026-05-13。适用分支：当前 jk_standard_rl 工作树。

检查结论

当前每步 RL 成本评估的主调用链是正确接通的：训练环境在执行动作后会先调用 evaluate_action_for_cost，该函数把动作解码成各 block 的噪声配置，再通过 RescaleOptimizerBridge 走 in-process 的 replan_with_user_actions。 返回结果再被解析成 total_bits_sum、total_fusion_count、 any_invalid 和每个 block 的 invalid_chain。

本轮审计发现并修复了一个确定的映射 bug：static_skeletons baseline 读取路径里，RO 节点 ctct_wo_rescale 曾错误映射到不存在的 wo_result_rescale_sf。现在已改为真实 RL 字段 wo_rescale_sf，并补了回归测试。

一条动作的完整管道

1. policy 输出离散动作向量 a，每个元素是索引，不是 scaling factor。
2. 解码动作action_vector_to_cfgs 读取 MaxSFsTable，生成每层 block 配置。
3. 建请求build_optimizer_requests 生成 block*_L* 请求，并跳过 layer-0 block1。
4. 映射到 RObridge 把 cfg 翻译成 t_new 与 delta_overrides。
5. 真实重规划InProcessInvoker 调 replan_with_user_actions 计算链合法性。
6. 聚合信号解析每个 block 的 bits、fusion、invalid，再汇总给 reward。

关键代码入口在这些文件： blb_stage2_rl/env.py 的 BLBStage2Env.step， blb_stage2_rl/optimizer_cost.py 的 evaluate_action_for_cost， blb_stage2_rl/action_space.py 的动作解码与请求构造， 以及 rescale_optimizer_bridge.py 的 cfg 到 RO 输入映射。

RL 动作坐标系

RL 看到的是一个离散动作向量。设第 j 个 slot 的离散维度为 m_j，动作索引为 a_j ∈ {0, 1, ..., m_j - 1}。 它本身不是 Rescale_Optimizer 能理解的节点名，也不是最终模数链。

非 rescale 槽位：
sfj = max_sfj - 2 · ( mj - 1 - aj )
rescale 槽位：
aj = 0 ⇒ 关闭该 BLB rescale 噪声 aj > 0 ⇒ sfj = max_sfj - 2 · ( mj - 1 - aj )
截断槽位：
kj = K_LEVELS [ aj ]

这里的 max_sf_j 来自 MaxSFsTable。当前训练启动时， baseline 会从 Rescale_optimizer/configs/<dataset>/static_skeletons_<dataset>.json 读取并校准，使 baseline 动作的最大索引对应 RO 给出的 baseline scaling factor。

Rescale_Optimizer 输入坐标系

Rescale_Optimizer 的 replan_with_user_actions 不接受 RL 动作向量。 它接收的是每个 graph 的 ReplanInputs，核心是两类量：

RO 输入含义由 RL cfg 的哪类字段得到
t_new baseline skeleton 上每个 stage 的目标输出 scale。长度为 R + 1，其中 R 是该 skeleton 的 rescale stage 数。 fresh 起点与落在 skeleton cut point 上的 rescale 字段，例如 gelu_out_fresh、mean_result_rescale。
delta_overrides 乘法节点传播 scale 时使用的增量。CTPT 是 plaintext 操作数 scale；CTCT 可以是 "x2" 或外部 ciphertext scale。 encode 字段和少量固定 CTCT 语义，例如 wffn2_encode、ctct_square="x2"。
映射可以写成：
D (a;M,degree) = { cfgb,l | b ∈ B , l ∈ L } R ( cfgb,l ) = ( graph_keyb,l , t_newb,l , delta_overridesb,l ) Ob,l = RescaleOptimizer ( graph_keyb,l , t_newb,l , delta_overridesb,l )

其中 D 是 RL 侧解码函数，R 是 bridge 的语义映射， O 是 Rescale_Optimizer 返回的每个 block/layer 结果。

关键映射规则

config_name 到 graph_key

RL 请求会保留 layer 信息，例如 block1_mrpc_L3、 block3_exp_n4_L7。进入 Rescale_Optimizer 前，bridge 会剥掉 _L* 后缀，得到真实 graph key，例如 block1_mrpc、 block3_exp_n4。这样同一个 graph 可以复用于不同层，而输出仍保留 原始 config_name 便于聚合和定位。

block3 与 block5 的 degree 选择

block3 由 softmax degree 决定 graph，例如 block3_exp_n4。 block5 由 GELU degree 决定 graph，例如 block5_n2。 所以同一个动作向量在不同 Stage-1 degree 下不能直接比较；graph key、skeleton 和 可用 rescale stage 都可能不同。

block4 的非对称 CTCT

ctct_rot_softmax_mul_v 是 softmax 与 V 的 ciphertext-ciphertext 乘法。 在 RO 图里它不是普通 encode 槽位，而是一个非对称 CTCT：主链从 softmax 一侧传播， V 侧以 other_ct_scale_bits 进入。当前 MRPC graph 的默认映射中， 该值固定为 39，代码注释和现有测试都把它视作 RO graph 约定。

这点容易误解：RL 的 block4 有 V 路径噪声动作，但当前 RO 成本图中 ctct_rot_softmax_mul_v 的外部 V scale 不是从某一个 RL V slot 直接反推出来的。 如果之后 RO 侧决定让它随 V 路径动作动态变化，需要先明确公式，再改 default_block4_cfg_to_delta。本轮没有擅自改这个语义。

Rescale_Optimizer 如何算 chain

对某个 graph，RO 拿到 skeleton S = [s_0, s_1, ..., s_R, sink] 和目标 scale t' = [t'_0, t'_1, ..., t'_R] 后，会重新传播每段 scale。

qr′ = PropagateScale ( tr-1′ , nodes_between ( sr-1 , sr ) ) - tr′ , r = 1 , … , R

PropagateScale 的规则是：

  • CTPT 乘法：s ← s + delta，其中 delta 来自 plaintext 操作数的 scaling factor。
  • 对称 CTCT：s ← 2s，代码里用 "x2" 表示。
  • 非对称 CTCT：s ← s + other，其中 other 是另一条 ciphertext 输入链的 scale。

如果任何 q'_r ≤ 0，或者某段 q'_r 超过 graph 的 q_max， RO 会直接返回 invalid。若某些 q'_r 小于 q_min，RO 会尝试把它融合到相邻 prime； 成功融合的次数就是 fusion_count。如果融合无法让链满足约束，RO 返回 invalid_chain 作为诊断。

valid ⇔ ∀ r , qfinal,r ∈ [ qmin , qmax ] total_bits = qhead + Σr=1R qfinal,r + qtail fusion_count = | { 被吸收到相邻 prime 的 rescale stage } |

返回值如何进入 RL reward

每个 block/layer 的 RO 输出先被解析成 RescaleOptimizerOutput： fusion_count 来自 RO 的融合事件数， total_bits 优先读 result.chain.total_bits， 若 invalid 则读 result.invalid_chain.total_bits，否则为 0。 valid 要求没有 invalid_chain 且 RO 标记有效。

聚合层做的是简单求和与计数：

total_bits_sum = Σb,l total_bitsb,l total_fusion_count = Σb,l fusion_countb,l any_invalid ⇔ ∃ (b,l) , validb,l = false

在 BLBStage2Env.step 中，如果 any_invalid 为真，环境会直接走 invalid reward， 不再安装 BLB 噪声、不跑模型 forward。若链合法，才把 RO 输出里的有效 rotation 反写到 cfg， 安装 BLB 噪声并做 probe evaluation。
